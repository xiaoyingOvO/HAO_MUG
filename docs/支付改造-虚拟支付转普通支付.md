## 零、现状：已按 3.2.2 的做法回滚

没有新写一套微信支付，而是**直接回到 3.2.2 的实现**：

| 环节 | 3.3.0（虚拟支付） | 回滚后（3.2.2 做法） |
| --- | --- | --- |
| 下单 | `cloudFcn.createPointOrder` → 云函数算 paySig/signature | `wx.cloud.callFunction({ name: 'cloudbase_module' })` → 跑云端工作流 |
| 拉起 | `wx.requestVirtualPayment` | `wx.requestPayment` |
| 到账 | 轮询 `queryPointOrder` 确认 | 不加轮询，刷新用户信息 + 提示「可能稍有延迟到账」 |
| 加点 | 云函数 `deliverByOutTradeNo` | 工作流的支付回调触发 `buyPoint` |

**改动只有前端 3 个文件**（`recharge.js` 607→443 行、`recharge.wxml`、`cloudFcn.js` 加注释），
云函数和 mock **一行都没动**。

### 为什么能这么轻

3.2.2 的普通支付不是自建的，而是**微信云开发的「工作流 + 微信支付」模板**：

```
前端 recharge.js
  └─ callFunction({ name:'cloudbase_module', data:{ name:'sywxzfapifqzf_73b1098', ... } })
       └─ 云端工作流：调微信支付下单 → 返回 prepay 参数
            └─ 用户付款 → 工作流收到回调 → 调 buyPoint 云函数加点
```

下单签名、回调验签、加点，全在云端工作流里，前端只负责「拿参数 + 拉起收银台」。
所以回滚 = 把前端那两处调用换回来。

关键前提已核对：**`buyPoint` 自 3.2.0 起从未改动**（`git diff d5cfbc8~1 HEAD` 为空），
工作流与它的契约完全没变，回滚不会打穿。

### 保留了什么（没有跟着一起回退）

| 改进 | 提交 | 说明 |
| --- | --- | --- |
| 单笔上限 1 万元，输入阶段即收敛 | `4d1c748` `c0e1462` `fae372b` | 输入框里显示的就是实际受理金额 |
| 「12.5 被洗成 125」的浮点处理 | — | 先切整数/小数再拼回，绝不直接删字符 |
| 长错误文案用弹窗完整展示 | `b29eaf9` | toast 会截断，长原因改用 modal |

顺带修了一个随回滚带出来的缺陷：微信支付失败的 `errMsg` 形如
`requestPayment:fail 签名错误`，**前缀 18 个字符**既没信息量、又把短文案顶过 12 字阈值，
导致所有支付错误都被判成「长文案」走弹窗。现在先剥前缀再判长度。

## 一、唯一的硬依赖：云端工作流还在不在

代码回滚完了，但**能不能真的收钱，取决于云端那个工作流还活着**。

```
工作流 ID：sywxzfapifqzf_73b1098
```

它不在 git 里（属于云开发控制台资产），3.3.0 改造时前端不调了，但工作流本身不会自动消失——
除非手动删过。

### 怎么查（3 分钟）

云开发控制台 → **工作流** → 找 `sywxzfapifqzf_73b1098`：

| 你看到的 | 结论 |
| --- | --- |
| 还在、状态正常、绑着商户号 | ✅ 直接编译即可，代码已经能用 |
| 还在但被停用 / 没有支付节点 | 重新启用并确认商户号绑定 |
| 找不到 | ❌ 见第二节，两条路选一条 |

顺便确认那个**商户号是普通微信支付商户号**，不是虚拟支付开通时系统发的二级商户号。
二级商户号收普通支付的钱，费率还是虚拟支付的，等于白改。

## 二、如果工作流已经没了

### 路 A：在控制台重建工作流（推荐）

云开发控制台 → 工作流 → 新建，照着 3.2.2 的结构配：

1. 触发节点：接收 `openid` / `point` / `description`
2. 微信支付节点：下单，金额 = `point × 100`（分）
3. 支付回调节点：调云函数 `baseFunctions` → `buyPoint`
4. 返回节点的 `data` 必须包含 `timeStamp` / `nonceStr` / `packageVal` / `paySign`

⚠️ 返回字段名是 `packageVal`（不是 `package`）——前端按这个名字取，再映射成
`wx.requestPayment` 的 `package`。字段名对不上会直接抛「获取支付参数失败」。

### 路 B：自建微信支付 V3（不依赖工作流）

只有在你想要「完全掌控签名和回调」时才值得走。工程量约 850 行，需要：

| 前置 | 在哪办 |
| --- | --- |
| 普通微信支付商户号 | pay.weixin.qq.com（营业执照 + 法人身份证 + 银行账户，1~2 工作日） |
| 商户号关联本小程序 AppID | 商户平台 → 产品中心 → AppID 账号管理 |
| APIv3 密钥（32 位） | 商户平台 → 账户中心 → API 安全 |
| 商户 API 证书 `apiclient_key.pem` + 序列号 | 同上 |

新增 `wxpay/{config,sign,http,order}.js` + `payNotify/` 回调，改
`createPointOrder` / `queryPointOrder` / `pointPayStatus` / `baseFunctions/index.js` / `cloudFcn.js` / `recharge.js`。

**好消息**：`xpay/pointService.js` 的 `deliverByOutTradeNo()` 是渠道无关的
（只做「读订单 → 按 exp 算赠送 → 事务加点 + 改状态」），两个渠道完全共用，一行不用改。
所以路 B 真正的增量是「下单签名 + 回调验签解密」，约 400 行，不是 850。

几个容易踩的点：
- V3 回调要回 **HTTP 200 + `{"code":"SUCCESS","message":"成功"}`**，不是虚拟支付的 `{ErrCode:0}`，否则微信一直重试
- 回调解密用 **APIv3 密钥**，不是 AppSecret
- **解密前必须验签**，否则回调可被伪造
- 金额全程用「分」

## 四、⚠️ 审核风险：3.2.2 就是被这个理由驳回的

这一点必须摊开说，否则会白走一圈。

事实链：

1. 3.2.2 提审 → 驳回，理由是「虚拟商品购买和支付均需接入官方小程序虚拟支付」
2. 于是改造成 3.3.0（虚拟支付）→ 申诉通过
3. 现在改回普通支付 → **如果什么都不改就提审，大概率收到同一条驳回理由**

因为审核看的是**页面呈现**：`1元=1点`（点成为独立计价单位）、有「点数转让」（可流转）、
没有一句「仅限本店消费」——这三条叠加就是虚拟代币的定义。

所以改支付通道**必须同时改产品形态**，四件事一起做：

| # | 改什么 | 怎么改 |
| --- | --- | --- |
| 1 | **计价单位** | 「点」→「元」（现在 1:1，纯改文案，账面无损失） |
| 2 | **转让功能** | 关闭，或加限额/白名单（代币可流转是资金转移的敏感特征） |
| 3 | **消费范围声明** | 充值页与卡券页加「仅限本店线下消费·不可提现·不可转让」 |
| 4 | **服务类目** | 移除虚拟类目，改「本地生活服务」下合适子类目（只需营业执照，不需要预付卡备案） |

补充：门店若有《娱乐经营许可证》，类目可以选到「游戏厅/棋牌」这类精确档位；
没有的话选「生活服务-其他生活服务」，需试审确认。
