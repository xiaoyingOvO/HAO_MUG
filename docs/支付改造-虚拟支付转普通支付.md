# 从虚拟支付切回普通微信支付：实施方案

> 背景：3.3.0 申诉通过，但虚拟支付抽成高（iOS 15% / 安卓约 1%），
> 而普通微信支付是 0.6%，且本项目业务实质是线下服务（游戏厅到店计时），
> 按《虚拟支付业务运营指南》本不在管控范围。
> 日期：2026-10-26

---

## 一、结论先说

**可行，而且风险可控。** 关键有利条件是：

> `xpay/pointService.js` 的 `deliverByOutTradeNo()` 是**渠道无关**的 —— 它只做
> 「读订单 → 按 exp 算赠送 → 事务加点 + 改状态」，完全不知道钱是从哪个渠道进来的。
> **这部分一行都不用改，两个渠道共用。**

改造范围因此收敛为三块：**下单签名、回调入口、前端拉起方式**。

---

## 二、收益与代价

### 收益

| 渠道 | 现在（虚拟支付） | 改后（普通支付） | 差额 |
| --- | --- | --- | --- |
| iOS | **15%** | 0.6% | **省 14.4 个百分点** |
| 安卓 | 约 1% | 0.6% | 省约 0.4 个百分点 |

附带收益：
- **退款自主**：现在 iOS 退款必须用户去 App Store 申请、由苹果裁决；改后可直接原路退
- **结算快**：现在 iOS 45~60 天，改后 T+3
- 不再受「虚拟支付开关不可关闭」「iOS 需开 IAP」这些不可逆约束

### 代价

| 项 | 说明 |
| --- | --- |
| 重新提审 | 改支付渠道必须重新提审，3.3.0 这个已通过的版本不能直接改 |
| 改类目 | 必须移除虚拟类目、加「本地生活服务」；类目变更本身会触发审核 |
| 产品形态调整 | 点数改元、处理转让功能、补「仅限本店消费」声明（否则会被判回虚拟） |
| 一次性工程量 | 约 850 行新增/修改，见第四节 |

## 三、前置条件（这些必须在动代码之前完成）

> ⚠️ **顺序不能反。** 代码改完但商户号没到位 = 支付彻底不可用，
> 而现在是能用的状态。**先备齐条件，再切开关。**

| # | 条件 | 在哪办 | 说明 |
| --- | --- | --- | --- |
| 1 | **普通微信支付商户号** | pay.weixin.qq.com | 需要营业执照、法人身份证、银行账户，审核 1~2 个工作日。**虚拟支付开通时那个二级商户号不能用于普通支付** |
| 2 | 商户号关联本小程序 AppID | 商户平台 → 产品中心 → AppID 账号管理 | 关联后小程序才能调用 `wx.requestPayment` |
| 3 | **APIv3 密钥**（32 位） | 商户平台 → 账户中心 → API 安全 | 用于回调验签/解密 |
| 4 | **商户 API 证书**（apiclient_key.pem） | 同上，申请证书 | 用于请求签名；私钥以文本形式放云函数环境变量 |
| 5 | 证书序列号 | 商户平台证书管理页 | 请求头 `Wechatpay-Serial` 需要 |
| 6 | **服务类目改为非虚拟** | MP 后台 → 设置 → 基本设置 → 服务类目 | 不移除虚拟类目，普通支付能力仍会被关闭 |
| 7 | 确认门店有《娱乐经营许可证》 | 门店证照 | 决定类目能选到哪一级细分（游戏厅法定要求） |

**第 1 条是硬门槛。** 如果目前只有虚拟支付的二级商户号，必须先申请普通商户号，
这一步没完成，后面的代码工作没有意义。

## 四、代码改造清单

### 4.1 双通道设计（核心思路）

不做「替换」，做「并行」，用环境变量切换：

```
PAY_CHANNEL = virtual   →  走现有虚拟支付（默认，保持线上可用）
PAY_CHANNEL = wxpay     →  走普通微信支付（条件齐备后切换）
```

好处：改造过程中线上始终可用；出问题改一个环境变量就能回滚。

### 4.2 改造后的调用链

```
前端 recharge.js
  ├─ pointPayStatus        →  返回 { enabled, channel, precision }
  ├─ createPointOrder      →  按 channel 分支
  │     ├─ virtual：现有 xpay 签名 → signData/paySig/signature
  │     └─ wxpay  ：微信支付 V3 下单 → prepay_id → 组装 payment 参数
  ├─ 拉起支付
  │     ├─ virtual：wx.requestVirtualPayment({ signData, paySig, signature })
  │     └─ wxpay  ：wx.requestPayment({ timeStamp, nonceStr, package, signType, paySign })
  └─ queryPointOrder       →  按 channel 分支查单
         ↓
  ┌──────────────────────┬───────────────────────┐
  │ xpayNotify（保留）     │ payNotify（新增）      │
  │ 虚拟支付消息推送        │ 微信支付 V3 回调       │
  └──────────────────────┴───────────────────────┘
         ↓                        ↓
  deliverByOutTradeNo()  ←── 同一个函数，渠道无关，不改
```

### 4.4 关键技术点

**（1）V3 请求签名**

```
签名串 = HTTP方法\nURL\n时间戳\n随机串\n请求体\n
签名 = Base64(RSA-SHA256(签名串, 商户私钥))
Authorization: WECHATPAY2-SHA256-RSA2048 mchid="..",nonce_str="..",signature="..",timestamp="..",serial_no=".."
```

**（2）回调解密**

回调 body 是 AES-256-GCM 加密的，用 APIv3 密钥解密，密钥是 `APIv3Key`（不是 AppSecret）。
解密前必须验签（用微信支付平台证书/公钥），否则可被伪造。

**（3）金额单位**

普通支付全程用**分**（`total_fee` / `amount.total`），现有代码已经在算 `amountCents`，
可直接复用，没有转换风险。

**（4）幂等**

复用 `deliverByOutTradeNo` 的现有幂等机制（事务内二次读 `state`），不需要重写。

**（5）回调必须返回 HTTP 200**

普通支付回调和虚拟支付不同：不是返回 `ErrCode=0`，而是要求 HTTP 200 + JSON
`{"code":"SUCCESS","message":"成功"}`。返回非 200 微信会重试。

## 五、产品形态要同步改的四件事

只改支付渠道、不改形态，下次审核还会被判虚拟。这四件必须一起做：

| # | 改什么 | 现状 | 改成 |
| --- | --- | --- | --- |
| 1 | **计价单位** | 「充值点数」「1元=1点」 | 「充值余额」「单位：元」 |
| 2 | **点数转让** | 有 `transferPoint` 页面 | 关闭，或加限额并明确「仅限本店消费抵扣」 |
| 3 | **范围声明** | 全项目零声明 | 充值页加「仅限本店线下消费，不可提现、不可转让」 |
| 4 | **优惠卡表述** | 「早八票」「夜场畅玩卡」 | 加一句「到店消费权益」，明确是线下服务折扣 |

第 1 条是零损失的（现在 1 元 = 1 点，改个单位而已），第 2 条需要产品决策。

## 七、风险与回滚

| 风险 | 应对 |
| --- | --- |
| 商户号申请被拒 | 保持虚拟支付，无损失（代码未上传） |
| 类目改不成功（无娱乐经营许可证） | 选「生活服务-其他生活服务」试审；仍不行则保持虚拟支付 |
| 普通支付上线后回调异常 | `PAY_CHANNEL` 改回 `virtual` 立即回滚，代码无需改动 |
| 审核仍判虚拟 | 说明形态没改干净，回去补第五节的四件事 |
| 已产生的虚拟支付订单 | `order` 集合的 `channel` 字段区分，老订单不受影响 |

---

## 八、一句话总结

> 技术上不难，难点在**后台资质和类目**，不在代码。
> 发货逻辑渠道无关，所以改造是「加一条通道」而不是「换一套系统」，
> 用 `PAY_CHANNEL` 开关切换，随时可回滚。
>
> **先确认商户号，再动代码。**
