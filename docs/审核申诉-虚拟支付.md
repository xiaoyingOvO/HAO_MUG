# 审核驳回申诉：虚拟支付

> 驳回原因：小程序服务内提供虚拟产品、虚拟商品购买服务，其购买和支付均需接入官方「小程序虚拟支付」能力。
> 状态：已选「我不接受，存在误判」，待补充反馈原因与证明材料。

---

## 一、先做 3 分钟自查（决定「申诉」还是「修好再交」）

代码侧已经确认合规：全项目 `grep wx.requestPayment` **零命中**（只有 mock 的 shim 和注释），
虚拟商品统一走点数，点数只能通过 `wx.requestVirtualPayment` 充值。

所以驳回只可能是下面三种情况之一。**第 1、2 种不是误判，硬申诉会被二次驳回。**

### 1. 云端配置没配齐 → 充值按钮其实是被置灰的（概率最高）

`pointPayStatus` 的判定逻辑：环境变量缺任意一个 → `enabled: false` →
充值页按钮变灰并显示 **「自助充值暂未开放」**。

审核员点进去看到灰按钮，就会认为「没有虚拟支付能力」，这跟驳回理由是吻合的。

**自查方法**：用真机或体验版打开 `我的 → 钱包 → 充值`，看按钮文案。

**✅ 已排除（2026-10-26 审核员截图）**：审核员截到的充值页，按钮显示的是
**「请输入金额」**（未输入金额的默认态），不是「自助充值暂未开放」。
说明 `pointPayStatus` 返回了 `enabled: true`，`XPAY_*` 环境变量是齐的，这条不成立。

| 按钮文案 | 含义 | 处理 |
| --- | --- | --- |
| 「立即充值 xx」/「请输入金额」 | 配置齐全 | → 属于误判或收银台没拉起，见下方 |
| 「自助充值暂未开放」 | 缺环境变量 | → **先补齐配置、上传云函数，再提审**，不要硬申诉 |

既然配置是齐的，那驳回只剩两种可能，**必须自己真机点一次才能区分**：

**A. 审核员没有真正点「立即充值」，只凭静态页面判断**
充值页通篇是「点」「1元=1点」，页面本身没有任何支付渠道标识，
审核员无法从这个画面判断你有没有接入虚拟支付 —— 大概率按模板驳回了。

**B. 点了，但虚拟支付收银台没弹出来（报错被吞成 toast）**
按 `recharge.js` 的流程，失败时只会弹一个 toast（2.5 秒后消失），
审核员看到「充值失败」类提示，同样会判「支付不可用」。

对照下面这张表定位（`_requestVirtualPayment` → `createPointOrder` 的报错文案）：

| 真机看到的提示 | 原因 | 处理 |
| --- | --- | --- |
| 虚拟支付未配置完成（缺少 XXX） | 环境变量缺项，且只在 `createPointOrder` 才暴露 | 补齐后**重传 baseFunctions** |
| 虚拟支付配置有误（道具单价非法） | `XPAY_GOODS_PRICE` 非正整数 | 改成 `100` |
| 充值金额需精确到 X 元 | 道具单价 ≠ 100 分，导致只能充整数元 | 与后台道具价格对齐 |
| 微信版本过低 | `wx.canIUse('requestVirtualPayment')` 为 false | 基础库需 ≥ 2.19.2 |
| 支付失败 -15011 | `XPAY_ENV` 填了 `1`（沙箱）但用的是现网版本 | 改成 `0` |
| 支付失败 -15001 / -15006 | OfferID / 道具 ID / AppKey 与后台不一致 | 逐个核对 |
| 该用户不存在 / 最高等级用户无需充值 | 审核账号数据问题 | 用普通测试账号 |


需要配齐的环境变量（云开发控制台 → 云函数 → `baseFunctions` → 配置 → 环境变量）：

```
XPAY_OFFER_ID        虚拟支付 OfferID
XPAY_APP_KEY         现网 AppKey
XPAY_PRODUCT_ID      道具 ID（后台创建的「点数」道具）
XPAY_GOODS_PRICE     道具单价（分），必须与后台道具价格完全一致
XPAY_ENV             0（现网；填 1 会报 -15011）
MP_APPSECRET         小程序 AppSecret（换 session_key / access_token）
```

改完环境变量**必须重新上传 `baseFunctions`** 才会生效。

### 2. 审核员没登录 / 没注册，根本走不到充值页

从驳回截图看，页面停在类似「请先注册会员」的状态。
如果充值入口必须先注册才能看到，审核员就不会去注册。

**处理**：提审时在「审核备注」里写清楚测试账号与路径，例如：

```
测试账号：138xxxxxxxx（验证码固定 1234 / 或已设为免密登录）
复现路径：底部「我的」→ 登录 → 钱包 → 充值 → 输入 1 元 → 立即充值
虚拟商品入口：钱包充值（点数）、会员页（优惠卡，用点数购买，不涉及人民币）
```

### 3. 确实是误判

前两条都没问题，那就是审核员按模板驳回的。走下面第二节的申诉。

## 二、反馈原因（上限 200 字，注意计数规则）

> ⚠️ 平台的字数是**按字符数**算的，英文单词 `wx.requestVirtualPayment` 一个字母算一个字（24 字），
> 上一版文案实际是 241 字，超了。下面两版都留了余量。

### 推荐版（实测 186 字）

```
小程序内虚拟商品（点数、优惠卡）统一以点数结算，点数仅能通过小程序虚拟支付
wx.requestVirtualPayment 充值，不存在 wx.requestPayment 等普通支付。已按官方文档
完成服务端签名（paySig/signature）、下单、回调发货与查单兜底。复现：我的→钱包→
充值，输入金额即拉起虚拟支付收银台。附件为后台配置、代码、收银台与到账截图。
```

### 保险版（实测 135 字，若上面仍超字就用这个）

```
虚拟商品（点数、优惠卡）均以点数结算，点数仅通过小程序虚拟支付
wx.requestVirtualPayment 充值，无 wx.requestPayment 普通支付。服务端已完成签名、
下单、回调发货与查单。复现：我的→钱包→充值。附件为配置、代码、收银台与到账截图。
```

要点说明（为什么这么写）：

- **先给结论再给证据链**：审核员不会去翻代码，必须让他知道「哪里能验证」。
- **明确说「不存在 wx.requestPayment」**：这是驳回原因的核心指控，要正面否认。
- **点名 `wx.requestVirtualPayment`**：驳回文案里的原词，直接对齐。
- **给复现路径**：把「你自己去看」变成可执行动作。
- **不要写「已经接入了」这种结论句**：审核员无法验证，只会当作辩解。

## 四、还要注意的两个连带风险

1. **云函数没上传 = 线上还是旧代码**
   如果 `baseFunctions` 一直是旧版，`pointPayStatus` / `createPointOrder` / `xpayNotify`
   可能根本不存在，充值页直接报错。这与 `docs/待处理事项.md` 的 A1 是同一件事。

2. **`MOCK_ENABLED` 必须是 `false`**
   `miniprogram/mock/cloudMock.js` 第 36 行当前是 `false`（正确）。
   如果曾经改成 `true` 并提交审核，整个支付链路会被 mock 顶掉，用户点了直接「到账」不扣钱——
   这种情况下驳回反而是对的。提审前务必确认这一行是 `false`，并重新编译。
