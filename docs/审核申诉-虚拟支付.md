# 审核驳回申诉：虚拟支付

> 驳回原因：小程序服务内提供虚拟产品、虚拟商品购买服务，其购买和支付均需接入官方「小程序虚拟支付」能力。
> 状态：已选「我不接受，存在误判」，待补充反馈原因与证明材料。

---

## 一、先做 3 分钟自查（决定「申诉」还是「修好再交」）

代码侧已经确认合规：全项目 `grep wx.requestPayment` **零命中**（只有 mock 的 shim 和注释），
虚拟商品统一走点数，点数只能通过 `wx.requestVirtualPayment` 充值。

所以驳回只可能是下面三种情况之一。**第 1、2 种不是误判，硬申诉会被二次驳回。**

### 1. 云端配置没配齐 → 充值按钮其实是被置灰的（概率最高）

`pointPayStatus` 的判定逻辑：环境变量缺任意一个 → `enabled: false` →
充值页按钮变灰并显示 **「自助充值暂未开放」**。

审核员点进去看到灰按钮，就会认为「没有虚拟支付能力」，这跟驳回理由是吻合的。

**自查方法**：用真机或体验版打开 `我的 → 钱包 → 充值`，看按钮文案。

| 按钮文案 | 含义 | 处理 |
| --- | --- | --- |
| 「立即充值 xx」 | 配置齐全 | → 属于误判，直接申诉 |
| 「自助充值暂未开放」 | 缺环境变量 | → **先补齐配置、上传云函数，再提审**，不要硬申诉 |

需要配齐的环境变量（云开发控制台 → 云函数 → `baseFunctions` → 配置 → 环境变量）：

```
XPAY_OFFER_ID        虚拟支付 OfferID
XPAY_APP_KEY         现网 AppKey
XPAY_PRODUCT_ID      道具 ID（后台创建的「点数」道具）
XPAY_GOODS_PRICE     道具单价（分），必须与后台道具价格完全一致
XPAY_ENV             0（现网；填 1 会报 -15011）
MP_APPSECRET         小程序 AppSecret（换 session_key / access_token）
```

改完环境变量**必须重新上传 `baseFunctions`** 才会生效。

### 2. 审核员没登录 / 没注册，根本走不到充值页

从驳回截图看，页面停在类似「请先注册会员」的状态。
如果充值入口必须先注册才能看到，审核员就不会去注册。

**处理**：提审时在「审核备注」里写清楚测试账号与路径，例如：

```
测试账号：138xxxxxxxx（验证码固定 1234 / 或已设为免密登录）
复现路径：底部「我的」→ 登录 → 钱包 → 充值 → 输入 1 元 → 立即充值
虚拟商品入口：钱包充值（点数）、会员页（优惠卡，用点数购买，不涉及人民币）
```

### 3. 确实是误判

前两条都没问题，那就是审核员按模板驳回的。走下面第二节的申诉。

## 二、反馈原因（可直接粘贴，约 185 字，上限 200）

```
本小程序所有虚拟商品（点数、优惠卡、场地预约）统一以点数结算，点数仅通过小程序
虚拟支付 wx.requestVirtualPayment 充值获得，代码中不存在 wx.requestPayment 普通
支付，也没有其他支付渠道。全链路已按官方文档实现：服务端用 OfferID/AppKey 计算
paySig、signature，完成下单、支付回调消息推送发货、查单兜底。复现路径：我的 →
钱包 → 充值。附件含虚拟支付后台配置、代码调用、真机收银台及到账记录截图，请复核。
```

要点说明（为什么这么写）：

- **先给结论再给证据链**：审核员不会去翻代码，必须让他知道「哪里能验证」。
- **明确说「不存在 wx.requestPayment」**：这是驳回原因的核心指控，要正面否认。
- **点名 `wx.requestVirtualPayment`**：驳回文案里的原词，直接对齐。
- **给复现路径**：把「你自己去看」变成可执行动作。

## 四、还要注意的两个连带风险

1. **云函数没上传 = 线上还是旧代码**
   如果 `baseFunctions` 一直是旧版，`pointPayStatus` / `createPointOrder` / `xpayNotify`
   可能根本不存在，充值页直接报错。这与 `docs/待处理事项.md` 的 A1 是同一件事。

2. **`MOCK_ENABLED` 必须是 `false`**
   `miniprogram/mock/cloudMock.js` 第 36 行当前是 `false`（正确）。
   如果曾经改成 `true` 并提交审核，整个支付链路会被 mock 顶掉，用户点了直接「到账」不扣钱——
   这种情况下驳回反而是对的。提审前务必确认这一行是 `false`，并重新编译。
