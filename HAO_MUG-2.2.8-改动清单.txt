一、这次改了什么
================================================================================

【1】排卡板刷新通道重做：5 秒轮询 → 数据库实时推送（实时是主通道，轮询只做兜底）

  问题：2.2.7 是「每 5 秒拉一次」，所以有人换了位置，别人最多要等 5 秒才看到。

  现在的主通道是云开发数据库的实时监听（watch）：
    · 页面打开时对「本机台的排队集合」建立监听，集合里任何一条记录变了
      （入队 / 退队 / 上机 / 位置调整），数据库**主动推**一个变更通知过来，
      页面立刻拉一次最新队列 —— 这就是你要的"真正实时"。
    · 收到推送后拉的是**全量**（走 getQueueInfo 云函数），不是只拿变更的那条。
      原因是排队集合里只存 openid / 时间戳 / 上机状态，**没有昵称和头像**，
      昵称头像是云函数按 openid 去 user 表拼的。

  【新增标识符（中英对照）】
    -- 页面侧（miniprogram/pages/queue-info/index.js）--
    · 集合名 queue_<机台ID>  = "单台机台的排队集合"，机台 M01 就是 queue_M01
    · ensureQueueRefresh()   = "打开刷新通道"（进页面时调一次，决定用实时还是轮询）
    · startQueueRealtime()   = "开始实时监听"（建立 watch）
    · stopQueueRefresh()     = "关闭刷新通道"（关 watch + 停轮询，离页调）
    · syncQueueRealtime()    = "跟随机台切换监听目标"（用户换了机台时调）
    · _queueWatcher          = "实时监听句柄"（关闭时要调它的 close()）
    · _queueWatchMachineId   = "当前监听的是哪台机台"
    · _queueWatchFailedMachineId = "哪台机台确认建立不起监听"（用来避免反复重试、刷日志）
    · watchEstablished       = "监听是否真的建起来了"（见下面【1.2】）
    -- 模拟层侧（miniprogram/mock/cloudMock.js）--
    · queueWatchers          = "监听登记表"（集合名 → 回调，模拟数据库的推送）
    · notifyQueueWatchers()  = "给某个集合的监听者推一次变更"
    · notifyAllQueueWatchers() = "给所有集合的监听者推一次变更"（重置假数据时用）

【1.1】兜底策略：先起轮询，监听生效后再停轮询

  建立监听是**异步**的。如果一进页面就只依赖监听，而监听建立失败或很慢，
  这段时间队列就完全不刷新了。所以顺序是：
    ① 先把 5 秒轮询起起来（兜底）
    ② 去建立实时监听
    ③ 监听真的建起来了 → 停掉轮询（省云函数调用）
    ④ 监听没建起来（离线模拟层 / 集合没配读权限 / 网络异常）→ 轮询继续跑

【1.2】修一个隐蔽的坑：监听失败时会把兜底轮询也一起停掉

  watch() 报错时，onError 可能在 watch() 返回之前就**同步**回调（集合没配读权限就是这种）。
  原来的写法是「onChange/onError 注册好 → 挂上句柄 → 停轮询」，
  于是 onError 已经退回轮询了，紧接着那行「停轮询」又把轮询关掉 ——
  结果就是：**既不实时、也不轮询，队列彻底不刷新**。
  现在用一个 watchEstablished 标志判断监听到底建起来没有，同步报错就直接 return，不动轮询。

【1.3】顺带把 2.2.7 里那两个空的方法删了

  onPullDownRefresh() / onReachBottom() 方法体是空的，没人调用（页面根本没开下拉刷新）。
  按"不留冗余"删掉。

【1.4】拖动时不打断

  拖卡过程中收到推送不会刷新列表（列表被重建会把拖到一半的卡弹回原位），
  松手后下一轮推送/轮询会补上。这是沿用 2.2.7 已有的处理。


【2】排卡板彻底关掉「下拉刷新」的观感和能力

  你说"还是有下拉刷新"，这次两面都堵死：
  · 页面配置 miniprogram/pages/queue-info/index.json 加 "enablePullDownRefresh": false
    （显式关掉页面级下拉刷新，不再依赖默认值）
  · 页面里两个 scroll-view 都加 bounces="{{false}}"
    （关掉滚动到头之后的橡皮筋回弹 —— iOS 上下拉时那个"像在刷新"的回弹就是它）

  两个 scroll-view：
    · .machine-list（左侧机台列表）
    · .queue-area（右侧排队区）


【3】离线模拟层补上数据库实时监听（watch）替身

  模拟层原来没有 watch 这个能力，导致离线调试时：
  · 页面每次都落到 5 秒轮询，控制台还会刷一条"实时监听不可用"的告警；
  · 你没法在离线环境里验证"实时推送"本身到底对不对。

  现在模拟层按真机的规则补上了：
  · 建立监听后先推一次 type='init' 的**首帧**（真机也是这个行为，用作进页面后的第一次刷新）
  · 排队数据真的被改写时推一次 type='update'
  · 返回 close()，页面离开时调用
  · **按机台隔离**：只有被改动的那台机台的监听者会收到推送，别的机台不受影响
  · 只读调用（getQueueInfo 等没动队列的）**不推**，不做无意义的刷新
  · wx.resetMockData() 也会推一次（队列被重置成初始数据）

  另外把假数据里误留的 "play_position: q.play_position,   // ← 加这行" 这句
  写代码时的临时注释删了。


【4】离线模拟层夜场票链路修复（2 个 bug）

  你说"夜场票现在购买了，晚上夜场还是显示夜场请预约无法入店"。
  离线模拟层这条链路上确实有两个 bug，都修了：

  【4.1】预约成功后不给 user.cards 发夜场卡
    云端 buyReserve 的 chargeReserve 里会 push 一张卡
      { card_id: 'e33be08d678e255a0189586d3b0d8a79', start_time, end_time }
    模拟层只加了预约记录、加了 exp，**没发这张卡**；而夜场判定（ifNight）是看
    "手里有没有在有效期内的卡"，所以模拟层里永远判定为"没卡"。
    现在模拟层也会发卡，时段算法与云端 chargeReserve 逐日核对一致。

  【4.2】夜场判定里写错了卡类型字段
    原来写的是  if (d.type !== 'hour') return false —— 但卡的类型在数据里是**数字**
    （0 = 每日时段卡，1 = 天数卡，见 addCard / buyCard），
    拿字符串 'hour' 去比数字，这个条件恒为 true → 直接 return false → 永远没有卡。
    现在直接按「当前时间是否落在卡的有效期内」判断。

  【新增标识符（中英对照）】
    · nightCardPeriod(reserveDay, duration) = "算出夜场卡的有效期"，
      入参 reserveDay 是预约日期（YYYY-MM-DD），返回 { start_time, end_time } 两个时间戳。
      算法：预约日当天 23:00 ~ 次日 10:00（与云端一致）。

  另外：这两处只影响**离线模拟层**（本地假数据）。云端 buyReserve / ifNight 的算法
  我逐日核对过是对的，详见下面第五节 —— 真机云端的问题还没定位，需要你配合看一个数据。

四、⚠️ 部署说明（必须做，否则实时推送不生效）
================================================================================

实时监听走的是**客户端数据库权限**（不是云函数权限）。
列表里的 queue_ 集合默认权限很可能是"仅创建者可读写"，那样前端根本读不到这个集合，
watch 会直接报错，页面就会**自动退回 5 秒轮询**（功能仍然正常，只是不实时）。

所以要让"实时"生效，需要去云开发控制台把每台机台的排队集合都改成"所有用户可读"：

  云开发控制台 → 数据库 → 找到 queue_ 开头的集合 → 权限设置 →
  选「所有用户可读，仅创建者可读写」

  本项目的排队集合（6 个，与机台一一对应）：
    queue_M01  舞萌·官机
    queue_M02  舞萌·MML
    queue_M03  舞萌·ADX
    queue_M04  中二
    queue_M05  麻将
    queue_M06  桌游

  如果以后新增机台，记得给新集合也配一遍。

判断有没有生效的最快办法：进排卡板，看控制台
  · 出现「队列变动触发刷新：init 0」 → 监听建立成功，实时生效 ✓
  · 出现「队列实时监听不可用，改用 5 秒轮询」 → 权限没配（或者网络问题）
刚进页面就会打印其中一条，不用等。

补充：包内小程序代码**不需要**重新部署云函数；只要在开发者工具里上传新版本即可。
（模拟层 MOCK_ENABLED 仍是 false，正式环境不会走假数据。）

五、夜场票（真机云端）—— 还没定位，需要你看一个数据
================================================================================

先说已经确认的部分：

【已经核对过的】云端这条链路的算法是对的。
  · 预约日期 D 送进云函数后，先转成 D 日 CST 午夜；
  · chargeReserve 生成的卡有效期 = **D 日 23:00 ~ D+1 日 10:00**（CST）；
  · ifNight 的"夜场"时段是 23:00 ~ 次日 09:59 —— 与卡的时段能对上。
  我用脚本按 3 个不同日期逐日算过，和模拟层实现完全一致（10 项断言全过）。

【也确认过的】夜场卡只有一条购买路径：预约页 → buyReserve。
  优惠卡列表里「夜场」是被 card.js 过滤掉、不展示的（card.js:105），
  所以不存在"从优惠卡列表买夜场卡、算出来的时段不对"这条路径。

【所以现在缺的是数据】需要你（或小影）帮忙看两处，任选一处即可：

  方案 A（最快，看数据库）
    云开发控制台 → 数据库 → 集合 user → 找到你自己那条记录 → 看 cards 数组
    里面应该有一条 card_id = e33be08d678e255a0189586d3b0d8a79 的记录，
    把它的 start_time / end_time 原样发我。

  方案 B（不用翻数据库，看日志）
    云开发控制台 → 云函数 → ifNight → 日志
    这个云函数里本来就会打印每一次判定的
        start_time: ...  end_time: ...
    在你说"晚上进不去"的那个时间点，它打印出来的那两个值是什么，发我。
    （如果一条都没打印，说明你那条 user 记录的 cards 是空的 —— 这也是很重要的信息。）

  另外麻烦一起告诉我：
    · 你预约的是哪一天？（比如"10-15 晚上"）
    · 你是在什么时间点试的入店？（比如 23:30 / 01:00）

【为什么先问不先改】
  最可能的两种原因，改法完全不同，改错了会把现在能用的路径弄坏：
    (a) 预约的日期和你试的时间不是同一场夜场（比如约的是明天、试的是今晚）；
    (b) 云端 card 集合里那张夜场卡配置的 duration.start_time / end_time
        存的不是"23 点 / 10 点"（比如存成了 UTC 口径的 15 点 / 2 点），
        那样算出来的卡时段会整体偏 8 小时 —— 这种情况要改的是**数据**，不是代码。
  拿到上面那个数据就能一眼分清。
